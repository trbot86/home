# Alexa capture backend checkpoint

2026-09-27. Local implementation for review by the main application task. No live
household was opened or migrated, and no Amazon/cloud/tailnet resource or credential
was created. All integration identities used in tests were synthetic and discarded.

## Implemented behavior

Migration 007 adds explicit integration actors and exclusive human/integration
ownership of clients, changesets and receipts. It preserves the old columns,
row identities, sequence high-water mark, reversal links, credentials, digests
and outcome JSON. Existing migrations 001–006 are unchanged. The referenced-table
rebuild checks foreign keys and integrity before commit, rolls back on failure,
and restores foreign-key enforcement. Production startup still refuses a pending
migration; the existing upgrade command verifies a backup before migrating.

Human request digests and history actor objects keep their original format.
Alexa history uses an integration actor labelled Alexa without adding a person,
private scope or administrator. Neither household member owns an Alexa action
for undo purposes; normal edits/deletions are attributed to the person making
them and retain their existing undo rules. Speaker recognition is deferred.

`IntegrationAccessService` provides explicit administrator-only provisioning,
rotation and revocation functions. Credentials use random bearer tokens and
stored SHA-256 verifiers. Rotation retains the client namespace. Both capture
and receipt resolution recheck expiry, revocation, enabled client and active
actor. These functions are not called on startup or exposed by an HTTP admin
route. A reviewed provisioning workflow is still needed for live setup.

`buildCaptureApp` constructs a separate Fastify server with two POST routes:

- `/capture/inbox` accepts operation ID, pinned epoch, inbox destination, text and
  capture time. It selects the shared scope, voice source and category, derives
  the inbox ID from client/operation identity, and accepts at most 1,000 characters.
  Known argument errors with a valid envelope receive durable rejection receipts.
- `/capture/resolve` returns only that integration client's receipt state for an
  operation ID and pinned epoch. It cannot retrieve a note's content or another
  client's receipts.

The listener rejects browser/Android credentials. Protected routes in the main
app reject integration credentials. Human-only repositories and commands also
reject integration contexts at runtime and through TypeScript types. The capture
server has no login, profiles, generic commands, media, history, backups, install
pages or static files. It uses a 16 KiB body bound, 60 requests/minute/IP, ten-second
request/connection limits and disabled request/error logging.

The separate built entrypoint is `apps/server/dist/capture-main.js`; the regular
app does not start it. It refuses to run without `CAPTURE_ENABLED=1`, an explicit
`DATA_ROOT`, matching `EXPECTED_INSTALLATION_ID`, and `CAPTURE_PORT`. It binds
loopback unless `CAPTURE_HOST` is explicitly set, and refuses an absent or outdated
database. Building it does not enable or deploy it.

## Verification

Workspace typechecking and package-boundary checks pass, along with 53 server,
6 Alexa and 5 contract tests. Server and web production builds pass. The sandbox
blocked esbuild's parent-directory resolution; the same local build passed with
filesystem escalation. Browser/device tests were not run in this worktree.
Existing web history renderers use `actor.displayName`; the native bridge passes
history through as JSON without requiring a human actor ID.

`apps/server/test/fixtures/pre-integration.json` is a fixed oracle generated by
the unchanged schema-006 code at revision `45a11ea`, committed before this
implementation. Its receipts/digests are not regenerated from the new code.
The tests in `integration-upgrade.test.ts` and `capture.test.ts` verify:

- Preserved old rows and values, synthetic media bytes, two profiles and sessions,
  private visibility, human actor shape and golden digests; legacy receipt replay
  and an unsent frozen Android request still work after upgrade.
- SQL actor constraints, sequence preservation with populated and empty history,
  failed backup refusal, injected SQL/FK migration failures, rollback, and restored
  enforcement. A verified post-upgrade backup restores into a new directory with
  the same installation and a new recovery epoch.
- One capture after a lost reply/retry, changed-payload conflict, no resurrection
  after human edits/deletion, Alexa attribution and unchanged human undo ownership.
- Credential separation, rotation/revocation/expiry/client/actor disablement,
  own receipt namespaces, private-scope/attachment/authority rejection, argument
  rejection receipts, body/rate bounds and internal runtime/type boundaries.
- A synthetic Alexa event reaches the real capture/write/receipt path through
  Fastify injection, then returns readback and ends the session. A repeat delivery
  produces no second changeset. No confirmation is required after saving.

## Remaining setup and integration work

The production `CaptureSink` transport, Lambda deployment, restricted tailnet
identity/policy and live provisioning workflow are not implemented. The account
and invocation/model setup remain user/device tasks. Amazon recognition, real
network timing and phone/speaker behavior are unverified.

The cloud identity must be denied every main-app listener: trusted-network login
can issue human sessions without a password, so merely handing the cloud a limited
token is insufficient. Local route tests do not verify this network restriction.
Review concrete cloud/service costs and deployment configuration before activation;
first exercise an isolated household and the deployed network policy.

When a new record kind is added by the main app task, include its record adapter
in capture construction for the shared completeness check (or factor shared
construction during integration). No generic feature handler belongs on this
listener. Re-run compatibility tests after integrating the main task's later
migrations and feature adapters.
